**От команд к полноценным диалогам: как я написал библиотеку для ботов на C#**

Однажды мне понадобилось написать бота для Telegram. Потом ещё одного. Потом третьего.

Предметные области у них были разные, но внутри повторялась одна и та же история: получить команду, задать уточняющий вопрос, дождаться ответа, проверить данные и решить, что делать дальше.

Пока бот отвечает на `/start` и показывает справку, всё довольно просто. Но стоит добавить регистрацию, создание заявки или настройку отчёта, как между сообщениями появляется состояние. Боту уже нужно понимать, на какой вопрос отвечает пользователь и что он успел выбрать на предыдущих шагах.

Затем появляются кнопки, списки, пагинация, возможность вернуться назад или отменить действие. По сути, мы разрабатываем пользовательский интерфейс, который живёт внутри переписки.

В какой-то момент мне захотелось выделить общий механизм, чтобы не писать его заново для каждого бота. Так появилась Telegram.Commands. Позже ядро было отделено от конкретного мессенджера, появился адаптер для Max, а общая библиотека получила название Bot.Commands.

В этой статье расскажу, как она устроена: от отдельных команд и сессий до событий, полноценных Fluent-сценариев и повторно используемых UI-компонентов.

**Сначала была команда**

Представим бота, который формирует отчёты. Для работы ему нужны период, подразделения и формат результата.

Можно предложить пользователю отправить всё одной строкой:

```text
/report 2026-10 sales,logistics pdf
```

Для разработчика удобно: разобрал аргументы, проверил значения, запустил обработку.

Пользователю придётся помнить синтаксис, порядок параметров и идентификаторы подразделений. Если отчёт нужен раз в месяц, к следующему запуску всё это вполне можно забыть.

Поэтому хочется организовать взаимодействие примерно так:

```text
Пользователь: /report

Бот: За какой период подготовить отчёт?
Пользователь: 2026-10

Бот: Выберите подразделения.
Пользователь: отмечает нужные кнопками.

Бот: В каком формате подготовить результат?
Пользователь: PDF

Бот: Отчёт за октябрь, подразделения — продажи и логистика.
     Всё верно?
Пользователь: Да
```

Для пользователя это один сценарий. Для приложения — несколько независимых входящих запросов.

Сообщение `2026-10` само по себе не объясняет, какой обработчик нужно вызвать. Выбранные подразделения необходимо сохранить до подтверждения. Некорректный период должен привести к повторному вводу, а кнопка «Назад» — вернуть к предыдущему шагу.

Так у бота появляется состояние.

**Диалог как конечный автомат**

Для небольшого сценария можно завести словарь с текущим шагом пользователя и написать `switch`. Это нормальное решение, и я тоже с него начинал.

Но когда сценариев становится больше, в них повторяется одна и та же инфраструктура: определить текущий шаг, получить сохранённые данные, обработать запрос и запомнить, чего ждать дальше.

Диалог подготовки отчёта удобно представить в виде конечного автомата:

```text
/report
   │
   ▼
Ввод периода ◄────────┐
   │                 │
   │ Ошибка ввода ────┘
   │
   ▼
Выбор подразделений
   │
   ▼
Выбор формата
   │
   ▼
Подтверждение
   │
   ▼
Формирование отчёта
```

Состояние определяет смысл входящего запроса. Результат обработки определяет переход.

Рядом с состоянием хранятся данные: выбранный период, подразделения, формат. Получается конечный набор управляющих состояний с дополнительным контекстом сценария.

В библиотеке я разделил эту модель на три части:

- **Команда** обрабатывает входящий запрос.
- **Сессия** хранит данные и информацию об ожидаемом обработчике.
- **Результат выполнения** определяет дальнейший переход.

Команда выполняет прикладную работу, а общий механизм применяет её результат к сессии.

**Откуда берётся текущая команда**

Есть два основных способа определить обработчик.

Первый — извлечь идентификатор из запроса. Пользователь отправил `/report`, и по имени можно найти соответствующий класс. Аналогичным образом действие может быть задано в данных кнопки.

Второй — посмотреть активную сессию. Пользователь прислал период, и приложение знает, что сейчас ожидается именно период отчёта.

Этим случаям соответствуют два интерфейса:

```csharp
IQueryCommand<TQuery>
ISessionCommand<TQuery, TData>
```

Обычная команда получает контекст запроса:

```csharp
Task<ICommandExecutionResult> Execute(
    IQueryContext<TQuery> query);
```

Сессионная команда дополнительно получает данные сценария:

```csharp
Task<ICommandExecutionResult> Execute(
    IQueryContext<TQuery> query,
    TData data);
```

`TQuery` — тип входящего объекта, например `Telegram.Bot.Types.Message`. Контекст предоставляет доступ к исходному объекту SDK и общей информации: идентификаторам пользователя и чата, содержимому запроса.

`TData` — обычный класс приложения. Библиотеке не нужно знать, какие именно данные мы собираем.

Для отчёта это может быть:

```csharp
public sealed class ReportData
{
    public string Period { get; set; }

    public string[] DepartmentIds { get; set; }
        = Array.Empty<string>();

    public string Format { get; set; }
}
```

**Три основных результата выполнения**

После обработки запроса команда сообщает, что делать дальше.

`Ahead` задаёт обработчик следующего запроса и передаёт ему данные:

```csharp
return CommandExecutionResult
    .Ahead<ReadPeriodCommand, Message, ReportData>(data);
```

Важная деталь: этот вызов не запускает `ReadPeriodCommand` немедленно. Он сохраняет информацию о том, кто должен обработать следующее подходящее сообщение.

`Freeze` оставляет метаданные текущей сессии без изменения:

```csharp
return CommandExecutionResult.Freeze();
```

Например, пользователь ввёл некорректный период, и нужно дождаться новой попытки. Срок ожидания при этом не продлевается.

`Break` завершает активную сессию:

```csharp
return CommandExecutionResult.Break();
```

Эти результаты управляют диалогом. Они не откатывают внешние действия: если команда уже записала что-то в базу или отправила сообщение, `Freeze` этого не отменит.

**Как начинается сценарий**

Посмотрим на команду запуска отчёта. Отправку сообщений вынесем в интерфейс приложения:

```csharp
public interface IReplySender
{
    Task Send(long chatId, string text);
}
```

Его реализация работает с клиентом мессенджера и регистрируется в DI.

Начальная команда задаёт вопрос и открывает сессию:

```csharp
[Command(Name = "report", Authorized = true)]
public sealed class ReportCommand : IQueryCommand<Message>
{
    private readonly IReplySender _sender;

    public ReportCommand(IReplySender sender)
    {
        _sender = sender;
    }

    public async Task<ICommandExecutionResult> Execute(
        IQueryContext<Message> query)
    {
        await _sender.Send(
            query.GetChatId(),
            "Введите период отчёта в формате ГГГГ-ММ.");

        return CommandExecutionResult
            .Ahead<ReadPeriodCommand, Message, ReportData>(
                new ReportData(),
                sessionDurationInSec: 300);
    }
}
```

Здесь и далее используются актуальные названия типов Bot.Commands. `Message` — тип из Telegram SDK. Примеры показывают отдельные части сценария; регистрацию сервисов и полный код приложения я оставляю за рамками статьи.

Атрибут задаёт имя команды без слеша. `Authorized = true` включает проверку через зарегистрированный `IAuthProvider`.

После выполнения команды бот ожидает ответ в течение пяти минут. Пользователю не нужно знать имя следующего обработчика: его определит сессия.

Внутри `ReadPeriodCommand` можно проверить ввод:

```csharp
var text = query.Query.Text?.Trim();

if (!DateTime.TryParseExact(
        text,
        "yyyy-MM",
        CultureInfo.InvariantCulture,
        DateTimeStyles.None,
        out var period))
{
    await _sender.Send(
        query.GetChatId(),
        "Не удалось распознать период. Пример: 2026-10.");

    return CommandExecutionResult.Freeze();
}

data.Period = period.ToString(
    "yyyy-MM",
    CultureInfo.InvariantCulture);
```

После успешной проверки обработчик показывает следующий вопрос или меню и возвращает переход к следующему шагу.

**Что сохраняется между сообщениями**

Сессия хранит сведения об ожидаемом обработчике, данные сценария, идентификаторы чата и пользователя, время жизни.

Привязка к паре «чат — пользователь» позволяет разделять диалоги участников одной группы.

Хранилище задаёт приложение через `ISessionsStore`. Для демонстрации достаточно памяти процесса. Если диалоги должны переживать перезапуск, нужна постоянная реализация.

В сессии стоит хранить данные сценария: введённые значения, выбранные идентификаторы, настройки интерфейса. Клиенты API и сервисы из DI должны оставаться в приложении.

Постоянное хранение также требует учитывать изменения кода. Если переименовать команду или изменить структуру данных, нужно решить, как поступать с уже открытыми сессиями.

**Другие команды во время диалога**

Предположим, бот ждёт период, а пользователь отправляет `/help`.

Что делать: показать справку, завершить сценарий или считать это некорректным периодом?

Обычная сессионная команда имеет приоритет перед новой командой из сообщения. Поэтому `/help` может попасть в обработчик ожидаемого ответа.

Если нужно управлять выполнением других команд внутри диалога, используется `IBehaviorCommand<TData>`.

Когда из запроса удалось определить команду, поведенческий обработчик получает её и решает, выполнять ли её и как поступить с текущим сценарием. Если отдельная команда не определена, вызывается обработчик по умолчанию.

Так можно задать общие правила: справка доступна без завершения диалога, отмена завершает его, а обычный текст считается ответом на текущий вопрос.

Этот механизм позже стал основой для `FluentCommand`. Но прежде чем перейти к нему, нужно учесть ещё один источник входящих запросов.

**События: когда пользователь не отправлял команду**

Бот реагирует не только на текстовые команды и нажатия кнопок.

Например, в группу добавили нового участника. Никто не отправлял `/welcome`, но приложению нужно показать приветствие, объяснить правила или выполнить действия в своей системе.

Для этого предусмотрены событийные обработчики. Они используют ту же модель команд, но выбираются по типу события.

Вместо `CommandAttribute` указывается `EventAttribute`:

```csharp
[Event(
    Type = EventType.ChatMemberAdded,
    Authorized = false,
    Area = ChatArea.Group | ChatArea.SuperGroup)]
```

Такой атрибут можно поставить на класс, реализующий подходящий `IQueryCommand<TQuery>`. Для события добавления участников в Telegram обработчик получает `Message`.

Адаптер распознаёт событие, после чего механизм находит совместимый обработчик. Извлекать имя команды из текста не требуется.

При этом сохраняется знакомая структура: контекст запроса, сервисы из DI, проверка метаданных и прикладной обработчик.

События имеют отдельный маршрут разрешения. Служебное сообщение о новом участнике не должно превращаться в очередную попытку ввода периода отчёта.

Теперь у приложения есть три источника выбора обработчика:

| Что пришло | Как определяется обработчик |
|---|---|
| Явная команда или callback | По идентификатору в запросе |
| Ответ внутри диалога | По активной сессии |
| Событие мессенджера | По типу события |

Поддержка событий зависит от адаптера. Например, добавление участника в Telegram представлено сообщением, а в адаптере Max — отдельным типом `UserAddedUpdate`. Наличие значения в общем `EventType` само по себе не означает поддержку всеми адаптерами.

В текущей реализации выбирается один совместимый событийный обработчик. Рассылки всем подписчикам нет, а `Order` не задаёт последовательный запуск нескольких обработчиков. Если обработчик не найден, событие игнорируется.

**FluentCommand: целый сценарий внутри одной команды**

Отдельные команды удобны, когда шаги достаточно самостоятельны. Но если каждый шаг — один вопрос и небольшой обработчик, множество классов начинает мешать видеть сценарий целиком.

А сценарий может быть гораздо сложнее линейной анкеты.

В нашем примере пользователь выбирает параметры отчёта, возвращается к периоду, меняет подразделения, открывает справку и только потом подтверждает запуск. В другом боте он собирает заявку из нескольких товаров, редактирует позиции и добавляет новые.

Для таких задач появился `FluentCommand<TData, TState>`.

Снаружи это обработчик, который участвует в общем механизме команд и сессий. Внутри — собственный конечный автомат с данными, сообщениями, кнопками и правилами переходов.

За одной пользовательской командой `/report` может находиться целый интерактивный сценарий:

```text
Ввод периода
      │
      ▼
Выбор подразделений ◄─────────────┐
      │                          │
      ▼                          │
Выбор формата                    │
      │                          │
      ▼                          │
Подтверждение ── Изменить выбор ──┘
      │
      ├── Изменить период → Ввод периода
      │
      ├── Отменить → Завершение
      │
      ▼
Формирование отчёта
```

Каждое состояние может содержать несколько сообщений, динамическую клавиатуру и обработчики разных действий.

Поэтому `FluentCommand` полезен не только для последовательного сбора полей. Через него можно описать форму настройки, мастер создания заявки, каталог с выбором позиций или меню управления сущностью.

**Вопрос и обработка ответа находятся рядом**

При ручной реализации логика одного экрана часто оказывается разнесена: сообщение отправляется в одном месте, клавиатура строится в другом, ответ разбирается в третьем.

В `FluentCommand` эти части можно расположить рядом:

```csharp
.State(ReportStep.Period)
.WithMessage(
    "Введите период отчёта в формате ГГГГ-ММ.",
    Send)
.WithCallbacks()
    .Row()
    .NextFromCallback(
        "Отмена",
        "cancel",
        ReportStep.Cancelled,
        true)
.Next<Message>(ReadPeriod, force: true)
```

Это фрагмент описания состояния. `Send` отправляет построенное сообщение, `ReadPeriod` проверяет ответ и возвращает следующее состояние. `Cancelled` нужно отдельно описать как состояние завершения.

Из кода видно, какой вопрос задаёт бот, что принимает в ответ и какое альтернативное действие доступно пользователю.

При ошибке `ReadPeriod` может вернуть то же состояние, при успешном вводе — состояние выбора подразделений. `force: true` позволяет повторно показать сообщение даже при сохранении текущего состояния.

Таким образом описываются развилки, повторные попытки и возвраты.

**Динамический экран вместо фиксированного вопроса**

Сообщения и клавиатуры могут зависеть от данных сценария.

На шаге подтверждения текст содержит выбранный период и подразделения. Набор кнопок определяется доступными действиями. Через `WithMessages` можно динамически построить несколько сообщений состояния.

Когда пользователь изменяет параметры и возвращается к подтверждению, содержимое строится заново из текущих данных.

Это позволяет описывать насыщенный интерфейс небольшим количеством состояний. Для каждой комбинации выбранных подразделений или каждой страницы списка отдельное состояние не требуется.

Точка входа `Entry` подготавливает данные и выбирает начальное состояние. Завершающие состояния описываются через `Exit`; их обработчики возвращают обычный результат выполнения команды.

Поэтому Fluent-сценарий можно завершить через `Break` или продолжить процесс переходом к другому сессионному обработчику. Для состояния, которое должно отправить сообщения и закончить работу без ожидания ответа, есть `FireAndForget`.

Получается самостоятельный участок процесса: он получает данные, проводит пользователя через свой граф состояний и возвращает управление общему механизму.

**Общие правила для всего сценария**

Поскольку `FluentCommand` построен на поведенческой модели, он поддерживает перехват запросов и команд.

`GlobalIntercept` позволяет выполнить общую логику до обработки текущего состояния.

`TryQueryCommandIntercept` управляет работой с распознанными командами: выполнять ли выбранную команду и должен ли её результат завершить или заменить текущий сценарий.

Например, можно один раз определить, что справка доступна на всех шагах и после её показа диалог продолжается. А результат команды отмены должен завершать сценарий.

Такие правила задаёт разработчик, но для них есть общее место. Их не нужно копировать в каждый обработчик ввода.

Именно сочетание этих возможностей делает `FluentCommand` центральным инструментом библиотеки: данные, ветвления, динамические сообщения, кнопки и общие правила объединяются в одном описании взаимодействия.

На этой основе становится удобно строить UI-компоненты.

**Внутри одного состояния тоже есть жизнь**

Вернёмся к выбору подразделений.

Пользователь раскрывает список, отмечает продажи, добавляет логистику, снимает одну отметку и только после этого нажимает «Продолжить».

Для сценария всё это один этап. Внутри него меняется интерфейс.

То же самое происходит с архивом отчётов: пользователь листает страницы, пока не найдёт нужную запись.

Поэтому полезно разделять состояние сценария и данные интерфейса. Состояние говорит: «выбираем подразделения». Данные содержат выбранные пункты и признак того, раскрыт ли список.

Действие пользователя меняет эти данные, после чего текущее состояние отображается повторно.

Именно на этом механизме построен `Bot.Commands.UI`.

**Dropdown из кнопок**

В UI-библиотеке есть `DropDown<TItem>` — модель раскрывающегося меню выбора.

Заголовок сворачивает или раскрывает список. Кнопки элементов переключают выбор. Доступны одиночный и множественный режимы.

Экран может выглядеть так:

```text
Выберите подразделения для отчёта

[ Подразделения: Продажи, Логистика ]
[ ✅ Продажи                       ]
[    Производство                  ]
[ ✅ Логистика                     ]

[ Продолжить ]
```

Модель такого меню:

```csharp
var departments = new DropDown<string>
{
    Title = "Подразделения",
    CallbackData = "departments",
    Show = true,
    Mode = DropDownMode.Multiple,
    Items = new[]
    {
        new DropDownMenuItem<string>
        {
            Item = "sales",
            Title = "Продажи",
            CallbackData = "sales"
        },
        new DropDownMenuItem<string>
        {
            Item = "production",
            Title = "Производство",
            CallbackData = "production"
        },
        new DropDownMenuItem<string>
        {
            Item = "logistics",
            Title = "Логистика",
            CallbackData = "logistics"
        }
    }
};
```

`Item` хранит прикладное значение, `Title` — подпись кнопки, `CallbackData` — значение для обработки нажатия.

В Fluent-клавиатуру меню добавляется через `AddDropDown`. Компонент создаёт заголовок, видимые элементы и обработчики переключения.

По умолчанию нажатие сохраняет текущее состояние сценария и вызывает повторное отображение. Можно передать свой обработчик, если изменение выбора должно выполнять дополнительное действие или приводить к переходу.

Выбранные значения доступны через модель:

```csharp
var departmentIds = departments
    .GetSelected()
    .Select(x => x.Item)
    .ToArray();
```

Саму модель нужно хранить в данных сценария либо восстанавливать из них с сохранением выбора. Если при каждом запросе создавать её заново с исходными значениями, отметки пользователя потеряются.

Приложение также определяет правила: обязательно ли выбирать хотя бы одно подразделение и что означает пустой выбор.

В компоненте предусмотрена настройка `NothingIsAll`, которая учитывает отсутствие отметок как «Все» при проверке и отображении. При этом `GetSelected()` возвращает именно отмеченные элементы, поэтому семантику пустого набора при формировании отчёта задаёт приложение.

**Пагинация без отдельных состояний для каждой страницы**

После формирования отчётов пользователю может понадобиться архив.

```text
Архив отчётов

[ Продажи за октябрь ]
[ Логистика за октябрь ]
[ Сводный отчёт ]

[ 1 << ] [ 2 < ] [ ·3· ] [ > 4 ] [ >> 8 ]
```

Для таких списков есть `KeyboardWithPagination`.

Данные сценария реализуют `IFluentPagination`, который хранит номер страницы:

```csharp
public uint PageNumber { get; set; }
```

Приложение передаёт функцию построения страницы. Она получает данные сценария, номер страницы и построитель клавиатуры.

В этой функции можно запросить записи из базы или API, добавить кнопки и вернуть общее количество элементов вместе с размером страницы через `IFluentPaginationMenu`.

Компонент добавляет навигационные кнопки. При нажатии он меняет `PageNumber` и инициирует повторное отображение того же состояния.

В итоге достаточно одного состояния «Просмотр архива», внутри которого пользователь может листать страницы.

Способ загрузки, сортировку и обработку изменения списка определяет приложение. Если нужно сохранять выбор записей между страницами, он также хранится в данных сценария: пагинатор отвечает за навигацию.

**Как UI связывается с автоматом**

И dropdown, и пагинация используют один цикл:

```text
Действие пользователя
        ↓
Изменение данных интерфейса
        ↓
Повторное построение текущего состояния
```

Переход на следующий этап нужен, когда пользователь завершил работу с экраном.

Поэтому UI-компоненты естественно встроились в `FluentCommand`. Для них уже существуют хранение данных, маршрутизация действий и повторное отображение.

Сценарий можно собирать из крупных частей:

```text
Ввод периода
      ↓
Dropdown выбора подразделений
      ↓
Кнопки выбора формата
      ↓
Подтверждение параметров
      ↓
Формирование отчёта
```

А для просмотра результатов использовать другой набор:

```text
Настройка фильтров
      ↓
Архив с пагинацией
      ↓
Действия с выбранным отчётом
```

Для меня это одна из самых интересных сторон библиотеки. Повторно используется не только механизм ожидания ответа, но и способы взаимодействия с пользователем.

**Кто отправляет сообщения**

Построенное описание сообщения ещё нужно передать в конкретный мессенджер.

Этим занимается отправитель приложения. Он использует клиент SDK и решает, отправлять новое сообщение или редактировать существующее.

Для dropdown и пагинации часто удобно обновлять одно сообщение, чтобы каждое нажатие не добавляло новую запись в переписку. Но библиотека не выбирает этот способ автоматически.

Сценарий определяет содержимое и реакции на действия. Отправитель определяет, как это содержимое показать средствами конкретной платформы.

**Общее ядро и адаптеры**

Первоначальная библиотека была привязана к Telegram. Позже команды, сессии, результаты выполнения и Fluent-механизм были выделены в общее ядро, а интеграции с Telegram и Max — в адаптеры.

UI-компоненты также работают поверх общих моделей.

При этом обработчик, принимающий `Telegram.Bot.Types.Message`, остаётся зависимым от Telegram. Для повторного использования нужно отдельно выделять общую прикладную логику и учитывать типы запросов и отправку сообщений каждой платформы.

Адаптеры предоставляют основу для такого разделения, сохраняя доступ к исходным объектам SDK там, где нужны специфические возможности.

**Что остаётся приложению**

Библиотека организует обработку команд и состояние взаимодействия. Доставку обновлений, хранение, отправку сообщений и прикладные операции обеспечивает приложение.

Для команд предусмотрены авторизация через `IAuthProvider`, ограничения по типам чатов и группы `Swarms`, позволяющие выбирать доступные реализации для разных ботов.

Есть и эксплуатационные задачи, которые механизм состояний сам по себе не решает.

Обновления одной сессии нужно обрабатывать согласованно. Повторно доставленный запрос не должен создавать дубликаты значимых операций. Библиотека не предоставляет автоматическую дедупликацию, блокировки сессий и повторные попытки.

Если приложение обслуживает несколько ботов, нужно изолировать их хранилища: общий ключ сессии содержит чат и пользователя, но не идентификатор бота.

Для постоянных Fluent-сессий необходимо сохранять не только прикладные данные, но и обёртку с текущим состоянием и информацией об инициализации.

Динамические клавиатуры также требуют внимания: порядок построения должен позволять корректно сопоставлять нажатия с действиями. UI-компоненты избавляют от повторяющегося кода, а правила работы с изменяющимися данными остаются в приложении.

**Что получилось**

Всё началось с желания не писать одинаковую логику для очередного бота.

Команды позволили выделить отдельные действия. Сессии связали запросы в диалог. События добавили реакцию на изменения в мессенджере. `FluentCommand` дал возможность описывать целые интерактивные сценарии, а UI-компоненты — собирать внутри них меню и списки.

Для бота с двумя независимыми командами такая модель может быть избыточной. Но когда пользователь заполняет форму, меняет параметры, возвращается назад и взаимодействует с несколькими экранами, общий механизм становится полезен.

Теперь, добавляя сценарий, я могу сосредоточиться на его поведении: какие данные получить, как их проверить, что показать пользователю и куда перейти после его действия.

А код, который превращает отдельные сообщения и нажатия в связное взаимодействие, остаётся общим для разных ботов.

**Запускаемый пример к статье**

Сценарий отчётов реализован в приложении [ReportsBot](examples/ReportsBot/README.md). Его можно запустить локально без токена: консоль показывает сообщения и нумерованные кнопки, а запросы проходят через настоящий адаптер Telegram или Max.

```sh
dotnet run --project docs/examples/ReportsBot -- demo telegram
dotnet run --project docs/examples/ReportsBot -- demo max
```

Отправьте `/report`, введите период и выбирайте кнопки командами `#1`, `#2` и так далее. В примере есть dropdown подразделений, изменение параметров перед подтверждением, `/help`, `/cancel`, архив с пагинацией и событийное приветствие. Для проверки пагинации создайте хотя бы четыре отчёта.

Приложение формирует CSV и HTML на демонстрационных данных. HTML можно открыть в браузере и распечатать в PDF; отдельного PDF-генератора в примере нет. Сессии и индекс архива хранятся в памяти до перезапуска, сами файлы сохраняются на диске.

Для запуска настоящего бота задайте свой токен в переменной окружения `TELEGRAM_BOT_TOKEN` или `MAX_BOT_TOKEN` и выберите режим `telegram` или `max`. Токенов в исходниках нет. Подробные инструкции и ограничения приведены в README примера.
